# Sync 完整性审查与原生化前置要求

审查日期：2026-11-13。对象：提交 `85e89b0` 的 `scdn-sync` 0.2.0。方法：检查发布、监听、分发、应用、恢复、报告及测试代码，完成 4 项模块级定向复现和 1 项真实 Linux/OpenResty 场景。未修改运行代码或生产服务，以下结果不能归为新原生模块的验证结果。

## 1. 结论

基本链路已经包含按节点加密、mTLS、请求验签、防重放、完整快照、版本单调性、Worker 准备、事务回退和持久恢复。缺口集中在业务可用性判定、完整失败状态、队列异常恢复、文件发布边界及长期运维。

建议在原生化之前先把这些行为写入协议和验收合同。原生插件可以解决安装与运行依赖问题，但直接迁移当前代码会把已有缺口一并带过去。

## 2. 已复现的关键缺口

### P1：applied 只证明配置生效，不能证明业务回源正常

真实多 Worker 环境先运行正常站点，再停止另一测试源站并把站点切过去。结果如下：

| 观察项 | 结果 |
| --- | --- |
| 更新前业务请求 | HTTP 200 |
| 更新后业务请求 | HTTP 502 |
| 同步健康探针 | HTTP 204 |
| Node 持久 applied | 指向新版本 |
| Master 收到的报告 | `phase = applied` |

原因：[`node/probe.lua`](../scdn-sync/lib/scdn_sync/node/probe.lua)访问专用 `/__scdn_sync_probe`；[`runtime/registry.lua`](../scdn-sync/lib/scdn_sync/runtime/registry.lua) 的探针只检查当前版本是否有该 Host 并返回版本头。HTTPS 额外核对证书指纹。[探针 location](../scdn-sync/conf/node-server-probe.conf)清空业务 rewrite/access 逻辑，不访问普通业务路径、源站、静态内容或 WAF/限速行为。

这不是配置没有应用，而是缺少独立的业务健康语义。不能把 `applied` 直接展示为“业务正常”。建议区分配置应用状态与业务健康状态；允许站点设置探测路径、期望状态/响应、TLS 校验策略、超时与失败阈值，再按策略决定保留新配置或回退。停用、删除或明确允许源站离线的发布也要有对应政策。

### P1：下载和前置校验失败缺少可见的远端状态

模块级复现：正常签名的发布在获取证书对象时发生传输错误。结果为 `reports = 0`、没有 journal，已记录 highest。旧配置不会被错误激活，但 Master 没有收到此次下载失败的阶段与原因。

原因：[`node/apply.lua`](../scdn-sync/lib/scdn_sync/node/apply.lua) 在 `download()` 完成后才建立报告预留和 journal；下载、解密、证书校验、静态目录校验等前置错误不走后面的应用失败报告。[Node 常驻进程](../scdn-sync/lib/scdn_sync/node/daemon.lua)会写受控本机错误日志并退避重试；当前 heartbeat 只包含已应用版本，没有失败阶段、最近一次同步错误、失败目标和重试状态。

建议增加有界、持久且可查询的 Node 同步状态，至少包含最近尝试的可信目标、阶段、受控错误码、失败时间与重试次数，并在 Master 汇总 desired/applied/observed 的差异。无法认证的清单不能自报其伪造 release_id 为可信发布失败，可上报节点级接收错误。

### P1：永久 4xx 会让队列头反复重试，阻断后续报告

模块级故障注入：队列中较早的 heartbeat 持续得到 409，后面有一条可接受的报告。连续 flush 三次，只发送了相同的 heartbeat，报告未发出；容量为 2 的队列保持满状态。满队列会阻止新应用。

原因：[`node/outbox.lua`](../scdn-sync/lib/scdn_sync/node/outbox.lua)对任何非 200 响应立即抛错，中止当轮发送，没有错误分类、队首诊断或安全的恢复流程。序号回退后的旧消息、协议不兼容、身份变更等都需要明确处理；不是所有 4xx 都适合无期限重试。

建议区分网络/5xx/429 重试、401/403 身份冻结与告警、409 幂等或序号冲突核对，以及无效业务消息的隔离。终态报告不能盲目丢弃或伪装已确认；heartbeat 可以设计为可合并的最新状态。补齐队列深度、最老消息年龄和阻塞原因，提供经过认证的查询/恢复操作。

### P1/P2：文件监听只有稳定窗口，没有跨文件提交边界

模块级复现：从两个站点开始，在 `allow_empty=false` 下临时移除一个站点文件，停顿超过稳定窗口后补回。发布的站点数依次为 `2 → 1 → 2`，中间版本会删除该站点。空目录保护不能识别这种非空的中间集合。

[`master/watch.lua`](../scdn-sync/lib/scdn_sync/master/watch.lua)的内容扫描和稳定窗口已经能处理单文件半写与快速编辑，但无法判断跨文件变更是否整体完成。手工调用 publish 已有完整输入边界；缺口主要在文件自动发布入口。

建议增加不可变发布目录与显式提交清单/标记，列出所有站点和证书摘要；完整校验后才发布。可另设大比例删除保护和 dry-run 差异预览。不能仅延长稳定时间代替事务边界。当前行为是已知设计限制，是否允许自动删除需要由部署策略明确。

### P2：多节点没有统一自动发布批次与灰度状态

同一文件变更向两个 Node 发布时，复现得到不同的 release_id。原因是 watcher 没有传统一的 release_id，而 [`master/publish.lua`](../scdn-sync/lib/scdn_sync/master/publish.lua)默认每节点随机生成；手工发布 API 已允许指定该字段。

当前逐节点发布能避免某个节点故障阻塞其他节点，但缺少这一轮发布的统一批次、目标列表、完成比例、超时、暂停/取消、灰度与主动回滚入口。

建议分开全局 batch_id 与每 Node 的 revision/desired_seq，由发布编排层提供批次目标和策略。保留“节点离线时其他节点可前进”，不把发布批次设计成所有节点必须同时在线的分布式事务。

## 3. 已验证的业务配置范围限制

对 [`validate.lua`](../scdn-sync/lib/scdn_sync/validate.lua) 的实际调用结果：

| 配置 | 当前结果 |
| --- | --- |
| 精确 Host：`www.example.com` | 支持 |
| 泛域名站点：`*.example.com` | 不支持；证书 SAN 通配符匹配与泛域名站点路由是两回事 |
| 源站：`origin.example.com:8080` | 支持 |
| HTTPS 源站：`https://origin.example.com:443` | 不支持此 schema；业务示例使用 HTTP proxy_pass |
| IPv6 源站：`[::1]:8080` | 不支持 |

当前站点 schema 还没有多源站池、负载均衡、备用源站、回源 Host/SNI、TLS 校验策略、自定义请求头、逐站点监听端口等完整描述。WAF 同步的是开关、组选择和阈值，限速同步的是请求速率与 burst；并不同步 WAF 规则正文，也没有实现连接限额。

如果产品只承诺现有 HTTP 站点范围，这些属于范围限制；如果希望“Master 定义的完整 CDN 站点都能在 Node 一致运行”，则需要先补配置模型及运行时能力，再谈字段同步。不能只是接受字段而不执行。

静态站点内容、Lua/模块程序更新、缓存文件、stream/RTMP、证书自动签发均不在当前协议范围内。它们可以有独立生命周期，无须为了插件化全部并入 Sync。旧 CLI 生成带 live/port_forward 等字段的站点放入同一 watcher 范围，会因严格字段校验而保留上一发布，需要导入审计和明确的托管范围。

## 4. 长期运行仍缺的能力

### P1：磁盘回收与容量保护

README 已明确没有历史 GC。自动续发仍会构建新 release 并重新加密证书，即使业务内容未变也会持续增加磁盘历史。队列和内存有界不等于磁盘有界。

需要保护 applied、journal、在途下载、回退窗口和未确认报告所需元数据，回收孤儿和临时对象，设置磁盘水位并在发布前预检空间。容量不足时保留已有业务配置并给出可见状态。

### P2：在途下载与版本保留协调

分发授权索引只保留当前及有限个最近版本；当前为最多 8 个。快速连续发布时，Node 刚获取的旧清单仍未过期，其证书对象可能已不在授权窗口，导致对象获取失败。当前可退避再尝试最新版本，但没有下载租约或在途版本 pin。

这是源码推导的边界，本次未额外进行高频发布与慢下载实测。需要把下载保留策略与 GC、撤销和容量预算一并设计，避免高变更率下长期追不上最新发布。

### P1/P2：密钥、身份和恢复生命周期

当前支持手工配置多把受信任发布公钥，但 Node 解密密钥、请求签名身份及 mTLS 身份仍以手工初始化/重载为主。缺少加入、替换、轮换重叠窗口、撤销传播及旧数据恢复的完整操作流程。

Master 从旧备份恢复后，发布序号可能低于 Node 已持久化的最高序号；Node/队列从旧备份恢复也可能落后于 Master 已接收的业务序号。现有单调检查会安全地拒绝回退，但没有完整的受控重新对齐流程。恢复方案应保留防回滚和权限验证，不能通过直接清空 highest 或复用旧身份绕过。

### P2：主动历史回滚和审计

当前 rollback 是本机当前事务的失败恢复，不是面向操作员的任意历史版本回滚。主动回滚应选择保留的完整输入，经授权后以新序号重新发布，并记录操作者、原因、差异与批次。Master 中仅保留旧的 Node 密文，不自动等于具备重新构建历史发布所需的全部源数据。

### P2：兼容性、查询和告警

协议固定版本不足以描述不同 Node 对站点 schema、算法、大小和功能的支持差异。原生化及滚动升级需要能力协商、最低版本约束、配置预检和兼容矩阵。

当前主要提供内部状态、心跳存储和日志，尚无完整的受认证运维查询、发布历史、每节点滞后/失败视图、指标与告警接口。至少应观测 desired/applied 差异、最近成功、错误阶段、报告积压、磁盘水位、证书到期与撤销生效情况。

### 按需求决定：高可用与同步加速

单 Master 当前没有跨机复制、领导者仲裁与 fencing。需要高可用时补充这些机制；简单增加第二个写入者会破坏版本和发布归属。现阶段不应把多 Master 作为基础插件的默认前置条件。

变更通知、长轮询、增量、断点续传与内容复用是规模优化。当前有界轮询和完整快照并非缺陷；应在正确性、恢复与容量边界清楚后按规模采用。

## 5. 建议的补齐顺序

1. **先明确成功与失败合同**：区分配置 applied 和业务 healthy；补前置失败状态、队列异常处理及最小查询/告警。
2. **再补发布边界与长期运行**：文件集合提交、批次与差异、删除保护、容量水位、受控 GC、历史回滚和恢复流程。
3. **固定产品配置范围**：逐项决定 HTTPS/IPv6 回源、泛域名和多源站是否属于首版；为混合版本 Node 加兼容预检。
4. **按上述合同原生化 Sync**：保留加密、身份、单调序号与事务隔离，迁移测试并验证 Lua/C 双向互通。

优先级需要结合用途：内部小规模同步可以把灰度和高可用后置，但业务健康语义、失败可见性、队列阻塞及磁盘增长应在长期使用或正式切换前处理。

## 6. 本次验证边界

4 项模块级复现分别覆盖前置失败报告、永久 4xx 队首阻塞、schema 支持范围、跨文件中间版本及关联批次行为；真实进程复现使用两个 Node、各两个 Worker、临时证书和 loopback 源站，验证不可达源站仍得到 applied。

这些定向复现未修改源代码，没有重新把已有 54 项模块测试和 48 项联调视为完整性证明。新增场景恰好说明原先通过的检查没有覆盖全部业务与运维合同。高频发布租约、真实跨机网络分区、ARM64、非 root 服务账户、磁盘真实掉电与容量上限仍需各自验证。
